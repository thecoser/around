# Feature requests from Around's development

These requests arise from observed work documented in [FRICTION-LOG](FRICTION-LOG.md). They are suggestions to Amazon, not Around features or claims of undocumented provider defects. Priority reflects the impact on this prototype.

| ID | Request | Amazon product or API | Why Around needs it and impact | Priority | Suggested behavior |
| --- | --- | --- | --- | --- | --- |
| FR-1 | Classified event scenarios across distinct simulated devices | Ring Developer Playground | The tested controls produced one-device live-view history. We could not validate a driveway/front-door visit using live classified events, so the positive story remains a labeled sample. | Important | Let developers select independent device IDs and emit documented person/vehicle/doorbell history or webhooks, including duplicates and delayed events. Keep live-view controls clearly separate. |
| FR-2 | Simulator quickstart and classified-history examples | Ring documentation | The public discovery path and subtype representation required separate investigation. This slowed the move from documented endpoints to a meaningful home-activity scenario. | Important | Link the Playground from hackathon setup, explain its event limits and show complete human/vehicle history responses plus `event_types` query examples. |
| FR-3 | More actionable playback diagnostics | Ring Playground | September 28 WHEP session creation returned HTTP 201 while the player reported “Unable to play media.” A September 30 recording later played successfully; the earlier cause remains unknown. | Nice-to-have | Distinguish session authorization, transport negotiation and player failures, with safe diagnostics that omit credentials. |
| FR-4 | Verification and authorization status before inference | Amazon Bedrock console and API | Early app calls returned access denial. The console later revealed account verification; a short-term-key rejection remained unexplained even after console inference succeeded. | Important | Surface verification state before test invocation and distinguish account verification, model access and bearer-permission failures without exposing secrets. |
| FR-5 | Minimal credential example for one model | Bedrock API keys, IAM and AWS SDK for JavaScript | The default LimitedAccess policy exceeded this MVP's needs. A separately approved narrow identity and one-day key enabled the app. | Important | Provide a single-region, single-model policy and SDK bearer-auth example alongside expiry and revocation instructions. State clearly which console identity creates the key. |

No request is marked Critical because the current disclosed prototype can be evaluated locally. Classified live-provider evaluation remains a validation gap, not something these requests claim to have solved.
